Workarounds outside the UI (LOCAL database only, as the bootstrap superuser):

- **Regime start month** (see D2): onboarding and *Agregar régimen* start every regime in the current
  month (October 2026) and the app has no way to change it, so records dated January–June are refused
  and earlier months cannot be estimated. After each taxpayer/regime was created in the app,
  `taxpayer_regimes.start_period` was set to `2026-01`.
- **Trial caps**: the golden inputs need 19 incomes and 7 expenses for one account; the trial allows 5
  of each. The user got a `comp` entitlement (the operator grant `data-model.md` documents for demo/QA
  accounts) instead of six sign-ups.

Direct API calls were only the flag-OFF probe. No seed scripts, no SQL inserts of records.

### Design review (estimate and breakdown)

The gstack `design-review` skill drives a browser against a URL, so it cannot run on emulator
screenshots; the screens were reviewed by hand from the screenshots instead. Good: one dominant
figure (*Total a pagar*), status chips in text, the CPA banner with icon and a red rule (not color
alone), amounts right-aligned with tabular digits, legend always visible. Issues: D3, D4; the totals
card shows no *Completo* chip when everything is complete (only the absence of "(incompleto)"),
which is easy to miss next to the per-regime chips.
