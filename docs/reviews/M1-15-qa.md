## 4. Issues

### Fixed (regression test first, one commit each)

| ID | Severity | Defect | Fix |
|---|---|---|---|
| F1 | Medium | Login `429` showed a static "Espera 3 min" that never moved (still "3 min" with 1:40 left), and **every tap during the wait went to the server**, spending the per-network login budget (20 / 15 min) that other users behind the same network share | `eb87d48`: login runs the same `Countdown` as the delete dialog (shared `RetryWait` widget, l10n key `authRetryIn`); a tap during the wait sends nothing and announces the time left. Test: `login_screen_test.dart` "too many tries count the Retry-After down…". Verified on device: live `0:37 → 0:28`, second tap sent nothing |
| F2 | High | Every countdown stuck at **"0:00" forever**: the login wait, the delete dialog wait, and the code step's "Otro código disponible en 0:00" — **the *Enviar otro código* button never appeared**, so a user whose code mail was lost could not get another. Cause: the periodic tick lands a few ms before the wall-clock deadline; `Countdown` saw 0 whole seconds left, cancelled its ticker while still running, and never notified again. Widget tests missed it because the fake clock and timers advance in lockstep | `aaa8230`: the ticker stops only when the wait is over and listeners are told when the running state flips. Test: `countdown_test.dart` "a tick just before the deadline still ends the wait for listeners" (clock 1 ms behind the timer). Verified on device: the resend button appears after the cooldown and works |

Docs (`ca389ab`): local-dev runbook gets the emulator path (10.0.2.2, the ~30 MB profile
build for low-storage emulators, where the verification code shows up); the mobile README
drops a stale "in memory until M1-12" line and documents the login wait.

### Deferred

| ID | Severity | Item | Owner / next step |
|---|---|---|---|
| D1 | Low (watch) | On the **first** cold start after sign-up, on the debug build, the app showed the login screen although the refresh token stayed on disk (the next launch restored it and refreshed normally). Not reproduced in 8 later cold starts (debug and profile). Most likely `sessionRestoreTimeout` (5 s) was exceeded by the first Keystore read during a slow debug cold start, so `restore()` fell back to signed out without deleting anything. Harmless for security, but a slow low-end phone would look logged out | frontend-sr: measure restore latency on a low-end device in a release build; consider staying on the splash while the read is still pending instead of a hard 5 s cut-off. Evidence `07`, `08` |
| D2 | Known (OB10) | Legal document links open `control-contable.invalid` (seeded placeholders, M1-03) | Real documents arrive with OB10 / REL-07 |

Delete-dialog `429` countdown was not driven on the device (6 more wrong passwords); it shares
the fixed `Countdown` and `RetryWait` and stays covered by `delete_account_dialog_test.dart`.
